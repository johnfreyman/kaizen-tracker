## Canonical records

These names are implemented in the isolated test SQL but remain subject to release review against an authorized deployed-like catalog. Every row carries `coach_id uuid NOT NULL`; every child uses a composite `(coach_id, parent_id)` foreign key so a supplied foreign UUID cannot attach another coach's data. Owner is always derived from `auth.uid()` by the server, never accepted as a client argument. UUIDs are client-generated once before local persistence, permitting offline creation. `0` and `00` are distinct text jersey numbers.

| Record | Key fields and constraints | Purpose |
| --- | --- | --- |
| `tracker_players` | `id uuid PK`; `(coach_id,id) UNIQUE`; `first_name`, `jersey_number text`, `short_label`, `is_guest`, `retired_at`, `legacy_name` | Stable identity. Reuse an existing `roster.id` only when one existing row unambiguously represents that player. Do not infer identity from name/number or reconstruct sample history. Number is player-wide, never repeated on a membership. Reject identical active display cards (case-insensitive first name + number + label); require a short label for a first-name/number collision. Retiring preserves all references. |
| `tracker_sub_teams` | `id uuid PK`; `(coach_id,id) UNIQUE`; `name`, `retired_at`; active name unique per coach | Named optional group. No sub-teams means the display-only default **Kaizen** group; it is not a fabricated membership row. |
| `tracker_memberships` | `(coach_id,player_id,team_id) PK`; composite FKs to player and team | Multiple simultaneous teams. Jersey number is absent. Membership removal changes future snapshots only. |
| `tracker_rounds` | `id uuid PK`; `(coach_id,id) UNIQUE`; `generation bigint`; `revision bigint`; `opened_at`, `closed_at`; partial unique index for one open round per coach | Exactly one current round for an initialized coach, even when raffle is disabled. No round is opened by toggling raffle off/on with **Keep**. Old rounds persist. |
| `tracker_sessions` | `id uuid PK`; `(coach_id,id) UNIQUE`; `session_date date`; `kind` Practice/Optional Training; `credit_hours numeric > 0`; `state` active/completed; `revision bigint`; `round_id`; `created_at`, `completed_at`; `archived_at` nullable; partial unique `(coach_id)` for server-active sessions | One session-hours record. New records use `1.5`; legacy varied credit remains exact. `round_id` is assigned once at start and cannot be edited. Archive is a reporting attribute, never an eligibility switch. Index `(coach_id,session_date,id)` gives deterministic same-day order without coach-entered time. Ordered offline replay completes A/B before starting C, so the one-active constraint does not discard pending local sessions. |
| `tracker_session_roster` | `(coach_id,session_id,player_id) PK`; name/number/guest snapshot, captured at start or first unexpected check-in | A roster fact at that session. Later rename/retirement does not rewrite display or guest classification for history. |
| `tracker_session_memberships` | `(coach_id,session_id,player_id,team_id) PK`; composite FK to session-roster and team | Membership set at that session, including both teams for shared players. This is independent of current `tracker_memberships`. Memberships should be copied for every snapshotted player, including an unexpected attendee on first mark. |
| `tracker_session_expected_teams` | `(coach_id,session_id,team_id) PK`; `all_kaizen` stored separately on session | The actual Who's expected? selection. Selected team IDs remain even if renamed/retired. |
| `tracker_session_expected_players` | `(coach_id,session_id,player_id) PK`; composite FK to session-roster | The resolved union saved once at start. Practice denominator/streak uses these IDs, not the coach's current roster or a report filter. No expectation rows for optional training. |
| `tracker_attendance` | `(coach_id,session_id,player_id) PK`; `present boolean`; `revision bigint`; `source_operation_id uuid` | Exactly one state per player/session. A present training attendance in a completed session earns one ticket by derivation; practice earns none. Marking absent/undoing updates the same row. |
| `tracker_operations` | `(coach_id,operation_id) PK`; `session_id` nullable; `device_id`, `device_sequence`, `kind`, `base_revision`, canonical request JSON, result JSON, `applied_at`; unique `(coach_id,device_id,device_sequence)` | Idempotency ledger. A duplicate ID with an identical request returns its stored result; reuse with a different request is a conflict. The ledger commits atomically with the mutation. No second write is inferred from a lost response. |

Future draw rows belong in Stage 6 but need stable `(coach_id,round_id,draw_id)` and a selected `(session_id,player_id)` ticket identity plus a frozen pool/revision, prize, display snapshot and void marker. A draw must never consume or delete attendance. Current ticket eligibility is a query over **completed** optional-training sessions assigned to the current round and **present** attendance, distinct by `(session_id,player_id)`. It ignores `archived_at` and `raffle_enabled`. Old-round edits affect only their old-round pool. Whole-program player-hours sum present `(session_id,player_id)` once; per-team history joins the session-membership snapshot and may overlap across teams, while whole-program totals are deduplicated.

## Transactional operation contract

Use a new versioned API. Do not modify the argument meaning of `save_session`, `remove_player`, or archive RPCs in Stage 3. Proposed entry point: a public `SECURITY INVOKER` wrapper with `EXECUTE` only for authenticated callers invokes a private, non-Data-API-exposed transactional function. Revoke the private function's default `PUBLIC` execution privilege and grant only the minimum privilege needed for the wrapper. The private function may use definer rights only with a fixed empty search path, schema-qualified object names, an explicit non-null `auth.uid()` ownership check and no client-supplied owner ID. Direct writes to canonical session/round/operation tables are revoked for browser roles; owner-scoped read policies remain. The isolated role tests must prove the wrapper's grants and all row policies, including the direct-table route. If this wrapper pattern is incompatible with the actual Supabase Data API configuration, revise it in isolation before committing SQL.

Every request includes an immutable `operation_id`, `device_id`, monotonic device sequence, operation kind, canonical payload and `base_revision`. Session operations also include the immutable `session_id`. Response includes `operation_id`, applied revision, canonical result and an explicit conflict code when rejected. Server processing is one database transaction: check authenticated owner and operation ledger, lock affected rows, compare revisions/dependencies, apply mutation, write the ledger result, commit. A duplicate returns the original result even if session state has since advanced. Rejected conflicts retain the local intent for review; they never silently last-write-win.

| Operation | Preconditions and effect |
| --- | --- |
| `start_v1` | Create supplied session UUID once with date, kind, 1.5 credit, cached round UUID, chosen team IDs and resolved expected-player IDs. Check every player/team/round belongs to the caller. Atomically save the **prepared-device snapshot** of roster identity and membership sets plus selected team IDs and expected-player union. An offline device may have an older but valid membership snapshot, so do not silently recompute its intended expected set from today's server roster; record cache version and flag any stale-snapshot conflict for review. Reject a same-ID/different-payload replay. A practice requires an explicit Who's expected? choice; training has no expected set. A stale cached round is **not** rebound to the new round: retain the original binding and return a reviewable `stale_round` status. |
| `set_present_v1` | Lock the exact session ID; require active state and matching base revision; upsert the one player/session attendance row to the desired boolean; snapshot an unexpected player and their memberships if not already present. Increment session revision once. Kiosk undo is the same operation with `present=false`. Duplicate operation is a no-op replay. |
| `finish_v1` | Lock the exact active session ID, require expected revision, mark completed once and freeze its revision. Never delete a coach-wide active-session row. Derived ticket/credit queries see this finalized record exactly once. A delayed finish for A cannot close or change newer B/C. |
| `correct_v1` | Later correction is an explicit versioned operation on the **same** completed session, with a new revision and audit record. It never changes `round_id` or original credit duration. Exact correction UX is Stage 4/6; no silent reopen. |
| `start_fresh_v1` | Require online verified owner, no known unsynced local work, no server-active session, and expected current round/revision. Atomically close that round and open exactly one next generation. Return new round ID/revision. Idempotent retry cannot open a second round. Server cannot detect a disconnected device's unseen outbox; a later old-round start must retain its cached old binding and surface reconciliation. |

`raffle_enabled` is independent of rounds. New coach settings default on; an explicitly saved legacy false remains false. Enabling from false offers Keep or Start fresh; Cancel changes nothing. Do not tie round generation to archive/restore. D03 applies only to an eventual initial conversion of sample legacy events: current unarchived training records may enter the initial current pool; archived history belongs to an older round. D11 means no real-history name matching or destructive cleanup is needed.

## Prepared iPad and outbox contract (D09)

Stage 4 will implement the client. Stage 3 fixes its wire/storage requirements:

1. While online, prepare and atomically persist an owner-namespaced cache: app shell/asset version, schema version, roster, memberships, settings, current round ID/revision, exit-code verifier, last successful sync and readiness result. Readiness is false if any required write or cache asset fails. Explicit logout prevents another coach from reading or replaying that owner's local data.
2. Each local intent is a durable transaction before success feedback: session snapshot/update plus immutable outbox entry and stable IDs. IndexedDB is recommended; the current single localStorage pending-event key is insufficient. A local failure shows a failure state and retains in-memory context without claiming durability.
3. Outbox order is global per owner/device, not merely per session: start A → marks A → finish A → start B → finish B → start C. A durably queued finish permits the next local start even if the network has not acknowledged it. Multiple finished sessions and active C coexist locally. Send one dependency chain at a time, or prove equivalent dependency-aware ordering.
4. A lost response retries the **same** operation ID and payload. Acknowledgment removes only that exact outbox entry; it cannot clear newer sessions, marks or kiosk binding. Reconcile server result to the canonical local session ID, not by date/name. Roster snapshots used while offline remain the original prepared values for that session.
5. On auth expiry, pause upload and retain the owner-scoped queue. After the same coach reauthenticates, resume. A different coach's login cannot read or submit that queue. Cache ownership is an offline display boundary, not remote authorization. App updates must preserve or explicitly migrate queue storage; an incompatible update blocks work visibly rather than deleting it.
6. Reset/draw requires online server acknowledgment of **all known** pending attendance and no active session. Offline and known pending work block these actions. A stale round after another device's reset is a recoverable conflict; the offline session's original round ID remains immutable and no ticket is silently moved to the newest pool.

Initial scope remains one attendance iPad per session. Same-session multi-device offline editing is unsupported, but the server still rejects stale revisions from another device. Clearing site data or losing the device can destroy unsynced local work; the app must explain this limit rather than promise server recovery.

## Isolated rehearsal and remaining release gate

The separate test project was inspected with [simplification-stage3-inspect.sql](simplification-stage3-inspect.sql) after loading the available legacy migrations 001–007 and 009. Migration 008 was blocked by automatic approval review because it installs a persistent daily purge capable of irreversibly deleting auth users and cascaded data; it was not retried or reconstructed. Migration 010 was also left out because it is a separate legacy destructive path. The test project is therefore **not** an exact clone. After the Stage 3 SQL, the admin aggregate view is inaccessible to `anon` and `authenticated` in this test project; production remains unverified. No super-admin fixture was created, and the production sole-admin check remains a release gate. The backend's verified membership check was not altered.

The versioned test SQL was applied three times to that project and exercised with invented coaches, players, teams and sessions under actual database `authenticated` role/JWT claims, plus an anonymous-execute check. See the rehearsal record for observed outcomes and gaps. Before a release migration exists, reconcile against an authorized deployed-like schema, settle the open policies and complete the cases below. The Supabase CLI was unavailable here, so the test SQL remains under `docs/` rather than `migrations/`.

- One player on Blue 6th and Blue 7th: one attendance, 1.5 player-hours and one ticket for one training; both historical team filters find the same snapshot; moving the current membership does not rewrite it.
- Practices A/C expect a player, B does not: A present and C absent yield 50% and B does not break their streak. Another player present unexpectedly is credited but not inserted into the frozen expected set.
- Start, mark, undo, finish and reset each repeated with the same operation ID: same result, one session, one attendance row, one round transition, no extra ticket/credit. Reusing an ID with changed payload fails.
- Offline queue A finished, B finished, C active on the same date: ordered replay keeps three IDs and C active; a delayed acknowledgment for A or retry of finish A cannot change B/C. Interrupted upload and auth expiry retain unsent operations.
- Coach A cannot read or mutate coach B's player/team/session/round with direct table queries, foreign IDs, RPC payloads or replayed operation IDs. Anonymous calls fail.
- Training while raffle off still accrues; Keep preserves its pool; Start fresh changes only round eligibility; archive/restore does not change pool membership; a corrected old-round training remains old-round. A stale cached round is reported and never remapped.
- Synthetic 2-hour old session retains 2 hours after correction; no legacy sample/test account is deleted or reidentified.

Run schema/security advisors after the isolated application. Only after all these pass should the SQL become a reviewed repository migration and the Stage 4 frontend handoff be marked unblocked.
