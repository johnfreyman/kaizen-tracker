## Canonical records

These names are implemented in the isolated test SQL but remain subject to release review against an authorized deployed-like catalog. Every row carries `coach_id uuid NOT NULL`; every child uses a composite `(coach_id, parent_id)` foreign key so a supplied foreign UUID cannot attach another coach's data. Owner is always derived from `auth.uid()` by the server, never accepted as a client argument. UUIDs are client-generated once before local persistence, permitting offline creation. `0` and `00` are distinct text jersey numbers.

| Record | Key fields and constraints | Purpose |
| --- | --- | --- |
| `tracker_players` | `id uuid PK`; `(coach_id,id) UNIQUE`; `first_name`, `jersey_number text`, `short_label`, `is_guest`, `retired_at`, `legacy_name` | Stable identity. Reuse an existing `roster.id` only when one existing row unambiguously represents that player. Do not infer identity from name/number or reconstruct sample history. Number is player-wide, never repeated on a membership. Reject identical active display cards (case-insensitive first name + number + label); require a short label for a first-name/number collision. Retiring preserves all references. Retire and restore are versioned operations (D15) that keep the same UUID; see below. |
| `tracker_sub_teams` | `id uuid PK`; `(coach_id,id) UNIQUE`; `name`, `retired_at`; active name unique per coach | Named optional group. No sub-teams means the display-only default **Kaizen** group; it is not a fabricated membership row. |
| `tracker_memberships` | `(coach_id,player_id,team_id) PK`; composite FKs to player and team | Multiple simultaneous teams. Jersey number is absent. Membership removal changes future snapshots only. |
| `tracker_rounds` | `id uuid PK`; `(coach_id,id) UNIQUE`; `generation bigint`; `revision bigint`; `opened_at`, `closed_at`; partial unique index for one open round per coach | Exactly one current round for an initialized coach, even when raffle is disabled. No round is opened by toggling raffle off/on with **Keep**. Old rounds persist. |
| `tracker_sessions` | `id uuid PK`; `(coach_id,id) UNIQUE`; `session_date date`; `kind` Practice/Optional Training; `credit_hours numeric > 0`; `state` active/completed; `revision bigint`; `round_id`; `created_at`, `completed_at`; `archived_at` nullable; partial unique `(coach_id)` for server-active sessions | One session-hours record. New records use `1.5`; legacy varied credit remains exact. `round_id` is assigned once at start and cannot be edited. Archive is a reporting attribute, never an eligibility switch. Index `(coach_id,session_date,id)` gives deterministic same-day order without coach-entered time. Ordered offline replay completes A/B before starting C, so the one-active constraint does not discard pending local sessions. |
| `tracker_session_roster` | `(coach_id,session_id,player_id) PK`; name/number/guest snapshot, captured at start or first unexpected check-in | A roster fact at that session. Later rename/retirement does not rewrite display or guest classification for history. |
| `tracker_session_memberships` | `(coach_id,session_id,player_id,team_id) PK`; composite FK to session-roster and team | Membership set at that session, including both teams for shared players. This is independent of current `tracker_memberships`. Memberships should be copied for every snapshotted player, including an unexpected attendee on first mark. |
| `tracker_session_expected_teams` | `(coach_id,session_id,team_id) PK`; `all_kaizen` stored separately on session | The actual Who's expected? selection. Selected team IDs remain even if renamed/retired. |
| `tracker_session_expected_players` | `(coach_id,session_id,player_id) PK`; composite FK to session-roster | The resolved union saved once at start. Practice denominator/streak uses these IDs, not the coach's current roster or a report filter. No expectation rows for optional training. |
| `tracker_attendance` | `(coach_id,session_id,player_id) PK`; `present boolean`; `revision bigint`; `source_operation_id uuid` | Exactly one state per player/session. A present training attendance in a completed session earns one ticket by derivation; practice earns none. Marking absent/undoing updates the same row. |
| `tracker_operations` | `(coach_id,operation_id) PK`; `session_id` nullable; `device_id`, `device_sequence`, `kind`, `base_revision`, canonical request JSON, result JSON, `applied_at`; unique `(coach_id,device_id,device_sequence)` | Idempotency ledger. A duplicate ID with an identical request returns its stored result; reuse with a different request is a conflict. The ledger commits atomically with the mutation. No second write is inferred from a lost response. |
| `tracker_exit_codes` | `coach_id uuid PK`; `mode` `default`/`custom`; `revision bigint`; `verifier_alg`, `verifier_iterations`, `verifier_salt bytea`, `verifier_hash bytea`, `updated_at`; CHECK `tracker_exit_codes_verifier_matches_mode` | D13 kiosk exit code. No row, or `mode = default`, means `0000`. `custom` always has a complete verifier and `default` has none; a NULL-safe check (`coalesce(…, false)`) enforces this even against the table owner. The table never holds a PIN. |

Future draw rows belong in Stage 6 but need stable `(coach_id,round_id,draw_id)` and a selected `(session_id,player_id)` ticket identity plus a frozen pool/revision, prize, display snapshot and void marker. A draw must never consume or delete attendance. Current ticket eligibility is a query over **completed** optional-training sessions assigned to the current round and **present** attendance, distinct by `(session_id,player_id)`. It ignores `archived_at` and `raffle_enabled`. Old-round edits affect only their old-round pool. Whole-program player-hours sum present `(session_id,player_id)` once; per-team history joins the session-membership snapshot and may overlap across teams, while whole-program totals are deduplicated.

## Transactional operation contract

Use a new versioned API. Do not modify the argument meaning of `save_session`, `remove_player`, or archive RPCs in Stage 3. Proposed entry point: a public `SECURITY INVOKER` wrapper with `EXECUTE` only for authenticated callers invokes a private, non-Data-API-exposed transactional function. Revoke the private function's default `PUBLIC` execution privilege and grant only the minimum privilege needed for the wrapper. The private function may use definer rights only with a fixed empty search path, schema-qualified object names, an explicit non-null `auth.uid()` ownership check and no client-supplied owner ID. Direct writes to canonical session/round/operation tables are revoked for browser roles; owner-scoped read policies remain. The isolated role tests must prove the wrapper's grants and all row policies, including the direct-table route. If this wrapper pattern is incompatible with the actual Supabase Data API configuration, revise it in isolation before committing SQL.

Every request includes an immutable `operation_id`, `device_id`, monotonic device sequence, operation kind, canonical payload and `base_revision`. Session operations also include the immutable `session_id`. Response includes `operation_id`, applied revision, canonical result and an explicit conflict code when rejected. Server processing is one database transaction: check authenticated owner and operation ledger, lock affected rows, compare revisions/dependencies, apply mutation, write the ledger result, commit. A duplicate returns the original result even if session state has since advanced. Rejected conflicts retain the local intent for review; they never silently last-write-win.

| Operation | Preconditions and effect |
| --- | --- |
| `start_v1` | Create supplied session UUID once with date, kind, 1.5 credit, cached round UUID, chosen team IDs and resolved expected-player IDs. Check every player/team/round belongs to the caller. Atomically save the **prepared-device snapshot** of roster identity and membership sets plus selected team IDs and expected-player union. An offline device may have an older but valid membership snapshot, so do not silently recompute its intended expected set from today's server roster; record cache version and flag any stale-snapshot conflict for review. Reject a same-ID/different-payload replay. A practice requires an explicit Who's expected? choice; training has no expected set. A stale cached round is **not** rebound to the new round: retain the original binding and return a reviewable stale-round status (`needs_round_review: true` in the result and the stored row; D14 below). |
| `set_present_v1` | Lock the exact session ID; require active state and matching base revision; upsert the one player/session attendance row to the desired boolean; snapshot an unexpected player and their memberships if not already present. Increment session revision once. Kiosk undo is the same operation with `present=false`. Duplicate operation is a no-op replay. |
| `finish_v1` | Lock the exact active session ID, require expected revision, mark completed once and freeze its revision. Never delete a coach-wide active-session row. Derived ticket/credit queries see this finalized record exactly once. A delayed finish for A cannot close or change newer B/C. |
| `correct_v1` | Later correction is an explicit versioned operation on the **same** completed session, with a new revision and audit record. It never changes `round_id` or original credit duration. Exact correction UX is Stage 4/6; no silent reopen. |
| `start_fresh_v1` | Require online verified owner, no known unsynced local work, no server-active session, and expected current round/revision. Atomically close that round and open exactly one next generation. Return new round ID/revision. Idempotent retry cannot open a second round. Server cannot detect a disconnected device's unseen outbox; a later old-round start must retain its cached old binding and surface reconciliation. |

`raffle_enabled` is independent of rounds. New coach settings default on; an explicitly saved legacy false remains false. Enabling from false offers Keep or Start fresh; Cancel changes nothing. Do not tie round generation to archive/restore. D03 applies only to an eventual initial conversion of sample legacy events: current unarchived training records may enter the initial current pool; archived history belongs to an older round. D11 means no real-history name matching or destructive cleanup is needed.

### Roster, sub-team, retirement, correction and PIN operations (rehearsed 2026-09-23 and 2026-09-24)

These use the same envelope (`operation_id`, `device_id`, `device_sequence`, `base_revision`, JSON `payload`) and the same `tracker_operations` ledger as the session operations, so replay and changed-payload behavior are identical across all entry points. Each is an authenticated-only invoker wrapper over a private definer function with an empty search path. The settings entry point is `tracker_apply_settings_operation_v1(operation_id, device_id, device_sequence, kind, base_revision, payload)`, with the same argument shape as the roster entry point.

Every entry point checks in this order: the payload shape first, then identity and state (the row exists and is the caller's, its revision, its retired state), and only then the new values (name, teams, card collision). A rejection therefore names its most basic cause. For example, a create that reuses an existing UUID fails as "id already exists" even when the name would also collide.

| Entry point / kind | Payload (full desired state) | Rules |
| --- | --- | --- |
| `tracker_apply_roster_operation_v1` · `create_team_v1` / `rename_team_v1` | `team_id`, `name` | Base revision 0 for create; current team revision for rename. Active names unique per coach, ignoring case and surrounding space. |
| `tracker_apply_roster_operation_v1` · `create_player_v1` / `update_player_v1` | `player_id`, `first_name`, `jersey_number` (required key; `null` = setup needed), `short_label`, `is_guest`, `team_ids` | One player-wide number (D08); only surrounding space trimmed, so `0` ≠ `00` (D02); identical active card rejected until a short label distinguishes it (R03); every team must be the caller's; a retired team cannot gain members; update needs the current player revision and replaces current memberships only. Session snapshots never change. An update to a retired player is refused (`55000`) until the player is restored. |
| `tracker_apply_roster_operation_v1` · `retire_player_v1` (D15) | exactly `{player_id}`; any other key is refused | Needs the current player revision. Sets `retired_at` and raises the revision. The UUID, current memberships, session snapshots, attendance, credit and tickets do not change. A ticket already earned in the current round stays eligible. Retiring a retired player → `55000`. The next prepared roster leaves the player out. The server still accepts a stale offline start or mark that names the player, so recorded attendance is never lost. |
| `tracker_apply_roster_operation_v1` · `restore_player_v1` (D15) | exactly `{player_id, short_label}`; the label is required and may be `""` | Needs the current revision. Clears `retired_at`, sets the label and raises the revision. Same UUID and memberships. If an active player already shows the same card (first name + number + label), the restore is refused with `23505 card collision: restore with a distinguishing short label` and nothing changes. The coach then picks a distinguishing label. No other player is edited and no second identity is made. Restoring an active player → `55000`. |
| `tracker_correct_session_v1` (`correct_v1`) | `changes: [{player_id, present, snapshot?}]`, optional `reason` (≤ 500) | Completed session only; base revision must match; one entry per player; a player new to that session needs an owned snapshot and is never added to the expected set. Updates the same attendance rows, raises the revision once and writes one `tracker_session_corrections` audit row (before/after, reason, from/to revision). Round, credit, kind, date, expected teams and players never change, enforced also by a trigger that even the table owner cannot bypass. Which sessions the UI offers for correction (P09 recommends the last one) is a Stage 4/6 choice. |
| `tracker_apply_settings_operation_v1` · `set_exit_pin_v1` (D13) | exactly `{verifier: {alg, iterations, salt, hash}}` | Needs the current exit-code revision (0 if the coach never changed it). Stores the verifier in `custom` mode and raises the revision. Replacing a PIN is another set; the signed-in coach does not need the old PIN. Result: `{mode, revision, updated_at}`; the verifier is not echoed. |
| `tracker_apply_settings_operation_v1` · `reset_exit_pin_v1` (D13) | exactly `{}` | Needs the current revision. Returns to `default` mode (`0000`), clears every verifier column and raises the revision. |

Rejections are Postgres errors with stable SQLSTATEs. Stage 4 should read the `code` field that PostgREST returns in the error body, not rely on the HTTP status alone:

| SQLSTATE | Meaning | Client response |
| --- | --- | --- |
| `23505` "operation id reused with different request" | Same ID, different intent | Client bug or corrupted outbox: keep the local intent and surface it for review; never resend with a new ID automatically. |
| `23505` card collision / name in use / id exists | Validation | Show the coach; a label or a different name resolves it. A restore collision asks for a distinguishing label. |
| `40001` | Stale revision (session, sub-team, player or exit PIN), completed session, stale round, or an active session blocking Start fresh | Conflict: refetch and show for review; never overwrite. |
| `55000` | Wrong state: correction of an active session; retire of a retired player; restore of an active player; edit of a retired player | Refetch and show the current state. Use `set_present_v1` for an active session; restore before editing. |
| `42501` | Not the caller's, not found, or not permitted | Ownership/auth problem: do not retry blindly. |
| `22023` | Malformed payload, including an extra key in a retire, restore or PIN payload, and a weak or malformed PIN verifier | Client bug. For a PIN, derive the verifier again with the format below. |
| `22P02` | A malformed UUID in a payload (standard Postgres code; not exercised by the suite) | Client bug. |
| `23514` | Protected history (credit, round, completed state), or a custom PIN without a complete verifier | Only reachable from privileged SQL; never from a client operation. |

### Kiosk exit PIN (D13) and the prepared-device PIN contract

The server never receives or stores the PIN. The device derives a verifier and sends only that:

- **Verifier format:** PBKDF2 with HMAC-SHA-256 (WebCrypto `deriveBits`), input = the PIN digits as UTF-8, random salt of 16–64 bytes, 100,000–2,000,000 iterations (use 600,000), output 32 bytes. JSON: `{"alg":"PBKDF2-SHA256","iterations":600000,"salt":"<base64>","hash":"<base64>"}`. The server checks the exact keys, the algorithm name, the iteration range and the decoded salt and hash lengths.
- **Test vectors** (600,000 iterations, 32 bytes; identical from Node WebCrypto, Node `pbkdf2Sync` and Python `hashlib`): `4827` with salt `a2FpemVuLXRlc3Qtc2FsdA==` → `f5sqB5UrkErch74HLptMMvuWzk17ToK5psamLw5Rn0o=`; `1359` with `a2FpemVuLXNhbHQtMDAwMg==` → `K9qgjwTJFuzpvsPCzM/NXI4gw/nUwtKgLOQcNvU/OHk=`; `7702` with `a2FpemVuLXNhbHQtMDAwYg==` → `lm17G4bpKVKDz+MFxHkTPGTcgERq5RsRAHMWld3Tiac=`.
- **Limit:** a four-digit PIN stays a supervised-kiosk convenience (D01), not a security boundary. Anyone who can read a verifier (the coach's own session or the prepared device's storage) can test all 10,000 PINs quickly. Do not describe it as strong protection.

Prepared-device contract for Stages 4–5 (defined here, not implemented):

1. While online, the prepared cache (D09 item 1) stores the coach's `{mode, revision, verifier}` from `tracker_exit_codes`. No row means `default` at revision 0. Refresh it on every successful sync.
2. Offline exit check: in `default` mode accept only `0000`. In `custom` mode derive the verifier from the entered digits with the cached salt and iterations and compare it with the cached hash; `0000` is then refused, so it is no bypass.
3. Set or reset the PIN only from coach Settings (outside the kiosk), with a signed-in coach, while online. The device sends a new operation ID and its cached revision. It updates its cache only after the server accepts: the returned `mode` and `revision`, plus the verifier it sent (or none after a reset). Do not queue a PIN change offline: another prepared device would keep a different exit code without warning.
4. A retry after a lost response reuses the same operation ID and payload and gets the stored result. `40001` means another device changed the PIN: refetch, update the cache, tell the coach, and let them decide whether to change it again.
5. A device that stays offline keeps the exit code it cached. A reset made on another device reaches it only after it syncs. If the coach forgets a custom PIN while the kiosk is offline, the kiosk stays bound until the device can sync after a reset. Stage 5 must present this recovery path clearly.
6. Logout removes the owner-namespaced cache, including the verifier (D09 item 1).

### Raffle round for backdated and offline-recorded sessions (D14)

No new SQL was needed; `start_v1` already implements D14:

- A training newly entered from paper sends the current round from the device's prepared cache. The server binds that round, whatever the `session_date`, with `needs_round_review = false`. Its tickets count in the current pool.
- A session recorded offline before another device's Start fresh syncs later with its cached old round. The server keeps that binding and sets `needs_round_review = true` in the stored row and in the start result. Its tickets stay in the old round. A retried delivery returns the stored result and never rebinds, and `tracker_session_round_immutable` stops any later change of round, even by the table owner.
- The server cannot tell a paper entry from an offline recording. A new entry made on a device whose cached round is already stale is therefore also flagged for review, never moved silently. Enter paper records after a sync to avoid that review.
- The review surface is the owner's sessions with `needs_round_review = true`; Stage 4/6 presents it. Start fresh is refused while any session is active on the server, and the client must block it while it knows of unsent work (D09 item 6).

## Prepared iPad and outbox contract (D09)

Stage 4 will implement the client. Stage 3 fixes its wire/storage requirements:

1. While online, prepare and atomically persist an owner-namespaced cache: app shell/asset version, schema version, roster, memberships, settings, current round ID/revision, exit-code verifier, last successful sync and readiness result. Readiness is false if any required write or cache asset fails. Explicit logout prevents another coach from reading or replaying that owner's local data.
2. Each local intent is a durable transaction before success feedback: session snapshot/update plus immutable outbox entry and stable IDs. IndexedDB is recommended; the current single localStorage pending-event key is insufficient. A local failure shows a failure state and retains in-memory context without claiming durability.
3. Outbox order is global per owner/device, not merely per session: start A → marks A → finish A → start B → finish B → start C. A durably queued finish permits the next local start even if the network has not acknowledged it. Multiple finished sessions and active C coexist locally. Send one dependency chain at a time, or prove equivalent dependency-aware ordering.
4. A lost response retries the **same** operation ID and payload. Acknowledgment removes only that exact outbox entry; it cannot clear newer sessions, marks or kiosk binding. Reconcile server result to the canonical local session ID, not by date/name. Roster snapshots used while offline remain the original prepared values for that session.
5. On auth expiry, pause upload and retain the owner-scoped queue. After the same coach reauthenticates, resume. A different coach's login cannot read or submit that queue. Cache ownership is an offline display boundary, not remote authorization. App updates must preserve or explicitly migrate queue storage; an incompatible update blocks work visibly rather than deleting it.
6. Reset/draw requires online server acknowledgment of **all known** pending attendance and no active session. Offline and known pending work block these actions. A stale round after another device's reset is a recoverable conflict; the offline session's original round ID remains immutable and no ticket is silently moved to the newest pool.

Initial scope remains one attendance iPad per session. Same-session multi-device offline editing is unsupported, but the server still rejects stale revisions from another device. Clearing site data or losing the device can destroy unsynced local work; the app must explain this limit rather than promise server recovery.

The separate test project was inspected with [simplification-stage3-inspect.sql](simplification-stage3-inspect.sql) after loading the available legacy migrations 001–007 and 009. Migration 008 was blocked by automatic approval review because it installs a persistent daily purge capable of irreversibly deleting auth users and cascaded data; it was not retried or reconstructed. No super-admin fixture was created, and the production sole-admin check remains a release gate. The backend's verified membership check was not altered.

The versioned test SQL was applied to that project three times on 2026-09-22, twice on 2026-09-23 and three times on 2026-09-24, and exercised with invented coaches, players, teams and sessions under actual database `authenticated` role/JWT claims, plus anonymous checks. See the rehearsal record for observed outcomes and gaps. Before a release migration exists, reconcile against an authorized deployed-like schema, settle the open policies and complete the cases below. The Supabase CLI was unavailable here, so the test SQL remains under `docs/` rather than `migrations/`.

- One player on Blue 6th and Blue 7th: one attendance, 1.5 player-hours and one ticket for one training; both historical team filters find the same snapshot; moving the current membership does not rewrite it.
- Practices A/C expect a player, B does not: A present and C absent yield 50% and B does not break their streak. Another player present unexpectedly is credited but not inserted into the frozen expected set.
- Start, mark, undo, finish and reset each repeated with the same operation ID: same result, one session, one attendance row, one round transition, no extra ticket/credit. Reusing an ID with changed payload fails.
- Offline queue A finished, B finished, C active on the same date: ordered replay keeps three IDs and C active; a delayed acknowledgment for A or retry of finish A cannot change B/C. Interrupted upload and auth expiry retain unsent operations.
- Coach A cannot read or mutate coach B's player/team/session/round with direct table queries, foreign IDs, RPC payloads or replayed operation IDs. Anonymous calls fail.
- Training while raffle off still accrues; Keep preserves its pool; Start fresh changes only round eligibility; archive/restore does not change pool membership; a corrected old-round training remains old-round. A stale cached round is reported and never remapped.
- Synthetic 2-hour old session retains 2 hours after correction; no legacy sample/test account is deleted or reidentified.

Run schema/security advisors after the isolated application. Only after all these pass should the SQL become a reviewed repository migration and the Stage 4 frontend handoff be marked unblocked.

Compatibility gaps found from source, to settle at release (production was not queried):

- The legacy source has no exit-PIN storage (`team_settings` in `001_schema.sql` holds only the team name, logo and raffle flag, and `src/app` has no kiosk PIN). Every coach therefore starts in `default` mode (`0000`) and no PIN data needs migration. The live `team_settings` columns are unverified.
- The legacy roster has no retired flag. Legacy `remove_player` (migration 010) deletes the roster row and scrubs history. It must be disabled or guarded before release; the new path offers retirement instead.
- The legacy purge (007/008) deletes auth users. Tracker tables reference `auth.users(id)` without `ON DELETE`, so purging a coach who has tracker rows fails on the foreign key instead of deleting history. Purge versus history preservation is a release decision.
- The ledger keeps every accepted request, including each PIN verifier ever set (never a plaintext PIN), readable by the owner. Release review may choose to redact old verifiers.
- "Hidden from future lists" is a prepared-roster rule on the client. The server still accepts a retired player in a stale offline start, a mark or a correction, so no recorded attendance is refused.
- The live schema, grants, `admin_coach_summary_view` access and the sole super-admin account remain unverified.

## Approved policy update and remaining choices

On 2026-09-24 the candidate SQL implemented them as the operations above (D14 needed no new SQL) and the role suite tested them (145/145 after each of the last two applications). Backdated creation and stale-round offline replay are tested separately. Sub-team retirement and PIN length/storage details are not additional approved product decisions; the verifier format above is an implementation recommendation. The kiosk URL is a Stage 5 presentation choice. D10 already resolves practice targeting through saved selected teams; generic filtering never changes expectations. Excused absence/correction and unexpected-attendee streak effects remain open for Stage 6 reporting. None is silently inferred from the prototype.
